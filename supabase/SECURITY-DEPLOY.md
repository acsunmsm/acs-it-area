# Despliegue de las correcciones de seguridad

1. Identifica las cuentas del capítulo autorizadas a editar publicaciones y consultar inscritos. En Supabase Auth asigna a esas cuentas el atributo **app_metadata.chapter_role** con valor **admin** u **organizer** mediante la API administrativa. Conserva el resto de los metadatos. Los usuarios deben renovar su sesión después del cambio.
2. Aplica la migración de esta carpeta primero en staging y después en el proyecto de producción antes de desplegar la aplicación. La migración requiere el propietario de la base de datos y se ejecuta en una transacción. Comprueba la lectura pública de las publicaciones, la edición por organizadores y la denegación de los datos de inscritos a una cuenta ordinaria.
3. La consulta pública acepta un DNI de ocho dígitos. El servidor busca por coincidencia exacta y muestra los certificados asociados. Aplica también la segunda migración si ya habilitaste la consulta por UUID.
4. Configura SUPABASE_SERVICE_ROLE_KEY solo en el servidor y conserva las variables públicas de Supabase. Las rutas públicas de escritura usan una cuota compartida en PostgreSQL. En Vercel se usa la cabecera de cliente que establece el proveedor. En otros despliegues solo configura TRUSTED_CLIENT_IP_HEADER si el proxy reemplaza esa cabecera y es el único punto de entrada. Sin cabecera confiable se usa una cuota por ruta compartida.
5. Comprueba en Google si sigue activa la clave del antiguo formulario PHP. Si está activa, revócala, configura RECAPTCHA_SECRET_KEY en los servicios que la utilizaban y prueba un envío legítimo. Git conserva la versión anterior del archivo.
6. Ejecuta npm ci, npm run lint, npm run test:carbonito, npm run test:security y npm run build. El despliegue debe incluir public/horario/vendor generado durante el build.
